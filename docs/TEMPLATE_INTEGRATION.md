# Template integration

DevOps Stack Composer integrates three public MIT repositories through locked,
file-and-process interfaces. It does not use Git submodules and does not copy their
source into this repository.

## Locked sources

The shipped [`templates.lock.json`](../templates.lock.json) pins:

| Adapter | Repository | Commit | Interface schema |
| --- | --- | --- | --- |
| Docker | `https://github.com/k4nul/docker-build-template.git` | `bbd6c4ba184c0e68dcaf65d4eb26ea622847c8c3` | `docker-env-v1` |
| Jenkins | `https://github.com/k4nul/jenkins-pipeline-template.git` | `e71cd88365484d9aba464db084437276d98ff0e0` | `jenkins-plan-json-v1` |
| Kubernetes | `https://github.com/k4nul/k8s-platform-template` | `2c2c306354615157208c76fc97846ed391392e51` | `k8s-plan-json-v1` |

Every entry also records adapter version, review date, SPDX license, and license-file
marker. Composition checks the resolved Git `HEAD` against the full 40-character pin
and verifies the declared license file.

## Source resolution

Sources are evaluated in this order:

1. repeated CLI overrides such as `--template docker=/path/to/checkout`;
2. `DEVOPS_STACK_DOCKER_TEMPLATE`, `DEVOPS_STACK_JENKINS_TEMPLATE`, or
   `DEVOPS_STACK_KUBERNETES_TEMPLATE`;
3. the matching repository below `/home/k4nul/git/devops`;
4. the commit-specific cache;
5. a fetch of the exact lock-file commit from its remote.

The cache defaults to `~/.cache/devops-stack-composer/templates`. Set
`DEVOPS_STACK_CACHE` to replace the complete cache root, or `XDG_CACHE_HOME` to use
`$XDG_CACHE_HOME/devops-stack-composer/templates`. A cache entry is separated by
template name and commit SHA.

`--no-fetch` makes resolution local-only. It does not relax commit or marker checks.
The default local path is a convenience for this workstation, not a CI dependency;
GitHub CI can use fixtures or fetch locked public commits.

Required markers prevent a directory with the right name but the wrong interface from
being selected. They cover each template's license and official validation/rendering
scripts. A selected checkout with a different commit is reported as a validation
failure and is not accepted as equivalent merely because its files look compatible.

## Interfaces actually used

### Docker build template

The adapter emits exactly the upstream 15-key `config/image.env` contract and stages
application context plus generated Docker assets for
`scripts/validate-build-plan.sh`. The executable wrapper delegates load builds to
`scripts/build-image.sh` and publication to `scripts/push-image.sh`. Platform, OCI
metadata, SBOM enablement, and provenance mode use official inputs.

The upstream template has no official cache from/to seam and no scan command. Cache
requests therefore fail instead of being silently ignored. The generated Jenkins
pipeline owns Trivy scanning after its single push and binds the report to the
resolved registry digest.

### Jenkins pipeline template

The adapter executes the upstream read-only JSON plan commands
`show-jenkins-job-plan.ps1` and `show-service-pipeline-plan.ps1`, then exercises
`export-jenkins-job-dsl.ps1` in an isolated archive of the locked commit. Their
sanitized summaries are diagnostics; application-specific pipeline and Job DSL files
are generated by the composer because the template does not expose a direct
application-pipeline write API.

JCasC and controller configuration are deliberately not imported. They remain an
external ownership boundary for plugins, agents, authorization, seed jobs, and
credential values.

### Kubernetes platform template

The adapter calls the template's read-only profile catalog, environment preset,
render-matrix, and platform-plan commands. It selects the `minimal-application`
profile with the template's `nginx-web` application as an integration probe, invokes
`render-platform-assets.ps1`, and then runs the template's rendered-bundle,
security-baseline, and placeholder validators. Only compact, sanitized facts are
stored in `k8s/platform-context.json`.

The isolated render uses a temporary validation-values file derived from public
examples with documentation placeholders replaced by reserved `.invalid` names. The
placeholder gate checks the rendered deployable `k8s/` tree, not the example input
files used to produce it.

Application Deployments, Services, ServiceAccounts, ConfigMaps, Namespaces, and
Kustomize overlays are composer-owned projections of the normalized model. The
upstream platform bundle is validation evidence, not copied wholesale into the
generated application tree. Helm output and cluster apply are not performed by the
adapter.

## Isolation and diagnostics

Upstream execution occurs under a temporary root with timeouts and a constrained
environment. Locked Git content is staged without repository output directories or
symlink traversal. Generated inputs are overlaid only in that temporary tree, and all
temporary content is removed after the command. No adapter writes to a source
repository.

Captured upstream output is bounded and sanitized before entering a diagnostic or
report. Volatile timestamps, source-machine absolute paths, credential-like keys,
authorization material, and token-like values are removed or redacted.

## Version changes

Only `devops-stack templates update --write` changes pins. That command compares each
pin with remote `main`, fetches changed candidates into a temporary cache, and verifies
their commit markers and license before atomically writing a project lock. An update
does not assert adapter compatibility; follow the review and test sequence in
[`TEMPLATE_UPGRADES.md`](TEMPLATE_UPGRADES.md).
